# Seguridad

## Backups
Tienen diferentes nombres, pero el usual es backups o snapshots. Se pueden usar en diferentes contextos para distintas cosas.

En base de datos, se tiene la parte de "Compute": el CPU y la memoria. Son los componentes volátiles de la arquitectura. Además de Compute, se tiene el Disco. En disco los archivos de la base de datos almacenados (datos e indices) están almacenados en formato del disco. 

Los índices se crean a partir de los datos. Perder un índice no causa gran problema. 

Si se quiere crear un backup, se puede crear un bakcup directamente de los archivos en disco duro. Al hacer esto con base de datos, hay que bajar el process de la base de datos. Hay que apagar los servicios. Primero, porque hay datos que pueden haber quedado sin hacer commit. Y segundo, porque puede que al realizar la copia puede haber un commit en medio de realizarse, y la copia puede quedar a mitad de la escritura.

Los dumps generan mecanismos curdos para insertar los datos. Si se hace un dump, se puede hacer un dump de data y un dump de schema. Data: datos por tabla. Genera muchos inserts. Si es sql, genera statements sql. Schema: definición de tablas, llaves, etc. Genera los create. El dump suele ser muy grande porque los statements sql son texto plano, y puede tener muchas veces la misma palabra reservada. Esto golpea el rendimiento del CPU, memoria y disco.

También se puede tener un read réplica, y cada cierto tiempo se rompe la conexión con el servidor principal, se hace el backup y se reestablece la conexión. También se pueden generar nuevos read replica continuamente en varias ubicaciones para ahorrar tiempo recuperándose.

En un entorno cloud, se puede hacer Golden Image o Vanilla Installation. Se  puede tener un AMI (Amazon Machine Image). Los logs pueden estar en storage baratos, porque no se necesita acceso aleatorio sino solo escribir al final rápido. Así los datos no tienen que competir con logs y sistema operativo.

A partir del Golden Image, al volver a instalar, se puede recuperar una máquina virtual con la misma configuración e información que se tenía antes que la máquina virtual se dañara. 

Los IOPS son persistentes, aunque la máquina se borre, reinicie o apague los datos estarán guardados. Sin embargo tener estos discos conectados es muy caro. 

Los instance storage, son discos volátiles. Si el cloud se cae o la máquina se apaga o reinicia, se pueden perder todos los datos. Sin embargo, esto reduce costos y aumenta velocidad, y para que funcione hay que ser más agresivo con el backup policy. 

También se puede aplicar on-premise. Se utilizan el mismo tipo de técnicas. 

Los backups se utilizan para casos de emergencia o migración de datos. 

Se puede hacer un dump de la base de datos y luego un restore en azure. Este proceso puede tardar 10 horas en total. Pero como 10 horas para una empresa financiera no es aceptable, se puede convertir la base de datos de azure en un read replica. Al estar sincronizadas y restaure las 10 horas, se hace un failover automático para que la base de datos de azure sea la primaria. Y mientras tanto, la base de datos va recibiendo las actualizaciones. Si no tiene buen rendimiento, se puede volver a hacer failover. 

Los bakups permiten migración incluso a otros motores de base de datos. 

## Stages (Fases) para crear backups
1. Identificar los data sources y la información importante para la empresa, ya sea tablas, instancias y logs.

Los logs de acceso corresponden a la información que van dejando los usuarios cada vez que se hacen accioens. Se hacen backups de todas las ventas y productos, pero los logs de acceso dejado por usuarios son igual de importantes. 

2. Se determina el tipo de backup.
3. Se elige el storage location
4. Se ejecuta el backup
5. Se validan los datos al restaurarlos en una ubicación distinta.

## Métodos de backups

Un backup **FULL** es muy caro porque necesitan recursos, espacio, y se necesita mucho tiempo, hay un gran efecto en cpu, memoria y disco. Sin embargo, permite recuperar todo completamente. Dura menos tiempo en restaurar, pero más tiempo en hacer backup.

Un backup **INCREMENTAL** crea un backup full el primer día. Luego el siguiente día, solo se crea el backup de la diferencia entre el último bakcup. Así que el primer bakcup es caro, pero el resto son pequeños y rápidos. Es rápido, tiene un bajo uso de recursos, pero la recuperación puede ser más compleja. Para recuperar la base de datos, hay que restaurar todos los backups en orden. Si se daña un backup en el medio, se tienen problemas porque se pierde la información y no se puede recuperar la información. 

Un backup **DIFERENCIAL** crea un backup full al inicio. En los siguientes backups en vez de crear una copia solo de la diferencia con respecto al anterior, crea una copia de todas las diferencias entre el primer backup full todas las veces. No usa tantos recursos como el backup full, pero no es tan rápido como el incremental. Aunque un backup en medio esté dañado, se pueden recuperar los datos. Así al restaurar, solo hay que restaurar el primer y último backup.

**Mirror backup** es copiar información de read réplica.
