**Memoria volatil** 
- Si la maquina se apaga, se daña etc. Van a perderse los dato almacenados en la memoria.
La memoria de dato o de indice se organizan dentro de un file system. Los mismos tendra archivos de random acces. Lo que quiere decir es que las operaciones de escritutras a disco van a persistir y ademas van a ser muy lentas.
- Si  quiere cumplir con ACID, una base de datos que esta recibiendo de uina aplicacion muchas escrituras, al ser escritas tienen que ser actualizadas en memoria y ademas en el file system.  Si la tabla esta normalizada, se tendran que hacer muchas operaciones a disco que generan que se vuelva lento
- Si te tienen binary log y se queire cumplir con ACID, el tiempo de escritura va a aumentar mucho por que se tiene que asegurar que los datos fueron escritos a disco principal.
- El binary log da una alternativa y una buena practiva, es tener separado los discos a dopnde se pueda posible. Es decir, tener un disco para binary log y otro para los datos. Aunque en el mayoria de setups se encuentran en el mismo disco.


### Almacenamiento por binary log 
Binary log: Archivo de acceso secuencial. Alamacena por medio de los ID asignados por las bases de datos a las transacciones. Es una herramiento que permite incrementar la velocidad de escritura y lectura sobre la base de datos in tener el riesgo de mucho timeout y garantizando la persistencia de los datos.

  - Empiezan con begin, luego todos los statemenos que involucran la transaccion y por ultimo un commit. 
  - Al ser un archivo secuencial representa que van a ir haciendo appends, es decir anadir al final. Y al ser secuencial se tienen con seguridad de el primer statement fue generado primero que el consecuente
  - **Transaccion** -> Es una operacion de modificacion de datos. (No una secuencia de statements)
    
![alt text](<Untitled Diagram-Page-14.jpg>)

Los que hace diferente de el alamacenamiento del binary log vs el file sistem, el bianry log es un solo archivo sy se va haciendo appends. En el file system, se tiene archivos por tablas etc por ello el almacenamiento e insercion se hacen siguiendo las reglas de una base de datos tradicional. En el binary simplemente se guardan.

Cuado se agrego la tranasaccion al bianry log (PASO 1) como segundo paso se van a actualizar los datos en memoria principal (Simplemente los datos vfan a quedar en memoria principal para quedar en el buffer) van estar guardados, teniendo en cuenta que pueden ser volatiles, los va a mantener hasta que se genere el paso 3 FLUSH de los datos o un FSINC, agarran los datos para persistirlos en disco. Y todas las transacciones de memoria van a poner commit en el binary log. Asi es como los datos van a quedar perisistentes.


Es relevante pues el tiempo de los datos en buffered puede ser bastante largos y durante este tiempo se recolecta los datos se pudo caer el buffer. Luego la base de datos al reiniciar va a revisar el binary log si hay transacciones que no se les hizo commit o el apend de commit, querra decir que los datos no llegaron a disco. 

La base de datos va a leer los record sin commit y los va ejecutando en orden para meterlos a disco.

##### Binary log como mecanismo de replicacion de datos
Entre dos bases de datos una va a estar activa, y la misma va estar enviando los datos a la que esta en stand by. Cuando alguien viene y hace escritura la bd activa pasa los records por medio del binary log. Me garantiza que si las dos bases de datos aplican las mismas operaciones del binary log, en algun momento se van a tene dos bases de datos iguales, teniendo backup y manera de replicar datos.

## Master-Slave Replication
Entre las bases de datos se pueden replicar datos. Tiene dos modos de operacion:

#### Asincrono
Se habla de tener un envio en batch. Va a completar una ventana de eventos dentro del binary log, es decir cuando se recolecto 5 megas de eventos se hara el envio de manera asincrona. El binary log del slave estara atrasado 5 megas del binary log del master. Se relaciona al RTO y RPO. Pues los mismos como regla de negocio. Esto hace un solo uso de red al tener un envio de golpe.
Puede ser riesgoso que la ventana va a poder perder muchos datos si pasa algo.

![alt text](<Untitled Diagram-Page-3.jpg>)

#### Sincrono
Apenas llega un evento al bianry log, de forma inmediata se envia al binary log. Se gastan mas recursos, pues utiliza la red cada que llega una solicitud. 

![alt text](<Untitled Diagram-Page-4.jpg>)

###### Switch Over
Va permitir cabiar el trafico en caso de que el master falle y lo redirige a otro punto. 
###### Fail Over
Siempre va a necesitar un witness/testigo/arbitro puede ser un slave, v a desempatar el voto  pues el failover es automatico, se debe tomar una decision. Tienen una pequena instancia de pocos recursos para el witness, el cual corre pruebas a las bases de datos conocidas como keep alive/health checks permiten determinar si un servidor se cayo. 
Gracias al witness se podra saber si hay problemas de comunicacion y de donde provienen.
Se tendra un load balancer, gateway o proxy haciendo pruebas si las bases estan arriba

## Data Partioning -> server owns partition
Se hace particionamiento de datos sobre servidores para sacar el maximos progvecho de hardware disponlible conm partiiones funcionando como master y slave.
Se utiliza una forma de agarrar una tabla y dividirla en pedacitos basados por una caracteristica que refleje los registros a dividir. Guardando cada division en servidores distintos. Si se quieren hacer replicacion se generan particiones secundarios alamacenadas en servidores distintos a la primaria. Los slave no estaran en stand by podran estar listos para consultas.
Esta solucion consume reursos en forma overhead.

#### Overhead
Puede generar el overhead, se hace una tarea pero se gasta tiempo extra en hacer una tarea. SOn tiempos y recursos que se gastan pero no se usan directamente en la funcion primaria de la base de datos.

### Read Only Replica
Es una base ded atos que no recibe updates perosi recibe consultas. Una ocnsulta de escritura puede enciar actualizaciones a la master y ella a la replica.  Se tendra **consistencia eventual**, si el batch dice que se va a esperar para enviarlos y si alguien mientras tanto hace una consulta en la slave no se recupera los ultimos registros.

- No es aplicable para SQL pues no se puede permitir que haya inconsistencia en una base SQL.

- El envio sincrono de los datos pero  no se maneja una confirmacion de escitura aun habrian consistencia eventual.

Si quiero mantener consistencia fuerte se debe tener un disco para la data y otro para el binary log. Hay que tener en cuenta que los clientes se quedan esperando una respuesta. Cuando esta en modelo en binary log, al escribir en el ya se puede saber que los datos son persistentes e indicarle al cliente que se genero bien. Y cuando escribe a la memoria le indica al cliente que todo fue exitoso esto sucede en paso 2 pues se tiene seguridad que el dato esta en el binary.
Ademas en paralelo los datos se envian a la slave sin esperar que se envien a memoria. La slave aplica el binary log, pone en memoria principal y notifica a la master que todo esta bien. Despues de estos pasos, se le dice a la APP que todo fue exitoso.

El **strong consistency** requiere de esos pasos pagando overhead estra para asegurarse que los datos llegaron bien.

## SQL-BASED Replication Middleware
Se tiene servidores independientes, sin saber que los otros existen. Todos son identicos, con componentes separados. En medio tienen un interceptor que es una pieza de software que esta al frente de los servidores, e implementa la misma interfaz que las bases de datos.  El interceptor habla el dialecto de la base de datos. Cuando se envia una operacion, las operaciones de modificacion (UPDATE O INSERT) van a enviarse a todos los servidores. Si es un SELECT se balancea la carga y se envia a un solo servidor. con eso se tiene la replicacion de las bases con misma informacion y fuerte consistencia.

## Synchronous Multimaster Replication
Cada servidor recibre sus inserts y updates; en caso de hacer una misma operacion, las tablas en las dos bases de datos se convierten un shared resource. Para evitar que no haya conflictos e incosistencia se juega con el tipo de algoritmo. Cuando llega la transaccion el servidor manda request al otro preguntando acerca de los recursos compartidos a utiliza. Se envia y aplica los cambios al otro servidor, y envia un release de T1. Y asi con las transacciones al mismo tiempo en la misma unidad de datos. Es decir bloquea los recursos. Como consecuencia sufren los clientes porque tienen que esperar las etapas de sincrinizacion.

Se puede utiizar un esquema  **low writes** y **high reads** pues no se genera una sincronizacion muy grande va a ser poco comun algun tiuempo de espera.
