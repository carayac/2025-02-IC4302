### Document Model

Corazon de la bases de datos documentales. Basados en modelos key-values, son campos únicos que representan la base de datos.

La base de datos documental se basa en el document model, y el se encarga de hacer la representación en formato JSON.

1. Se puede modificar la estructura del documento y modificar disarmaments.
2. Los documentos pueden tener diferentes campos
3. Se puede representar cualquier tipo de dato, se tiene una cuota superior de 16 MB los docs mayores a 16MB no se pueden almacenar dentro de mongo.
4. Cuando se tiene volumenes grandes se suele tener datos binarios (Imagenes, videos, audios, archivos ejecutables, lagun tipo de archivo custom (zip, targ)) cualquier archivo que no se pueda leer en texto plano.
    1. Cuando se tiene datos binarios en un json, se puede convertir el dato en Base 64. ### BJSON / Binary JSON

Es un documento que suelen ser grandes. Sucede cuando a la hora de construir el documento, se busca un forma en la cual se pueda convertir el doc en una representacion de documento mas amigable.

### Codificacion de un documento JSON

En BJSON se tendra 4 bytes que respresentan el tamano del registro. Es decir, convierto el doc en un registro.

Tendra un 1 byte que representa el tipo de field.

Tendra 2 bytes que representa el name del field. El nombre de un cmapo termina siempre en 0x00 el cual es el terminador de documento

Tendra 4 bytes para representar el valor del campo. A bajo nivel se maneja en little endian.

### RAW Dataset

Permite dividir los datos.

Se maneja shard key → define como una unidad se rutea o se guardan los datos. Se les establece id a los documentos cuando mongo lops recibe el podra saber en que shard guardarlo, los shard son replicas que se guardan en nodos de mongo. 

![alt text](image-8.png)

Se les asigna chunk, que tienen un limite de tamano. Automaticamente el wiredtiger divide el chunk en dos si este sobrepasa el limite de tamano. Se base en la cardinalidad de los datos con subdivision de los mismos con el mismo shardkey del principal.
![alt text](image-10.png)

Entre mas chunk se tenga va aser mas facil leerlo copmpleto y subirlo a memoria.

### JUMBO

Es un chunk muy grande que quedo asi pues el shard key no le pemitio hacerle la subdivision de los datos.

Cuando se ve un shard que no esta creciendo mucgo, mogo analiza si se puede hacer un reshard, y mover chunks para enviarlo a shards que no estan en uso.

Si el shard se hace muy grande, las consultas van a redirgirse a esos nodos buscando recursos y los peques van a estar desperdiciando recursos.

Es decir, se hacen un balanceo de shards.

### Tipos de servidores

Replica Set

No se tiene el concepto de shard. Es decir, cada uno de los servidores van a tener el 100% de los datos, siendo copias idénticas de los mismo. 

Replica Set Sharded

Se puede escoger cuanta replica de los datos por shard se pueden tener por servidor. Se puede definir la porcion de los datos que tendra cada shard, aumenta velocidad pero pierde disponibilidad.
